Attempted shortcut (2026-08-01, reverted): tried pointing st_common.c and unk_2697C.c at the
shared canonical `src/st/st_common.h` (the pattern every other ST overlay uses) to skip ~34
functions of manual decompilation. Failed for two independent reasons, both worth remembering:
  1. unk_2697C.c is a genuine SECOND physical copy of a subset of these functions at different

  2. Several of unk_2697C.c's functions (e.g. InitializeEntity) are called BY NAME from other

Real decompilation attempt (2026-08-01, reverted, lessons kept): tried e_room_fg.c
(EntityRoomForeground) and started e_room_bg.c (RLIB_EntityBackgroundBlock). Both have a
per-overlay rodata table (ObjInit-style struct array) driving the function. Manually decoded
D_us_801816D8 (e_room_fg's table, 6 entries x 20 bytes) word-by-word from the raw .word dump in
asm/us/st/rlib/data/6C4.data.s, and found the first 4 words of every entry matched EXACTLY the
hardcoded `eRoomForegroundInit[]` array already sitting in the shared `src/st/e_room_fg.h`
header (same pattern LIB uses: literally `#include "../e_room_fg.h"` with zero extra code).
Despite the apparent exact match, swapping rlib's e_room_fg.c to use the header still produced a
checksum failure (different SHA-1 than original). Reverted to the raw INCLUDE_ASM stub, back to
clean baseline.
**Important lesson**: manually verifying a data table's individual field VALUES match a
known-good source is NOT sufficient proof of byte-exact compiled output -- things like which
order the compiler lays out separate `static` sub-arrays (foregroundAnim1..5 in this case) in
.rodata, alignment, or subtle struct-packing differences can still cause a mismatch invisible
from reading hex dumps alone. Only a real WSL build+SHA1 compare is proof, never manual
inspection, no matter how confident the byte-level analysis looks.
**Pace note for future sessions**: unlike bo0's functions (mostly self-contained logic), a
sizeable fraction of rlib's remaining functions are these `Entity*Init`-table-driven ones, each
requiring manually decoding a per-overlay rodata table from a combined `data/*.data.s` file
(not split per-symbol) before any C can be written -- this is much slower per function than
typical decomp work. Realistic estimate: real progress on 148 functions will take multiple
sessions, working in small verified batches (1-5 functions between each real WSL build+diff),
not a single continuous push.

Took ~8 WSL round-trips. Key fixes along the way, useful for the next 147 functions:
1. extern-declare pre-existing rodata symbols (D_us_801807A4/AC/B4) instead of redeclaring as
   local static arrays -- a local redeclaration adds real .rodata bytes and shifts every later
   symbol's linked address (caught via 128-byte drift in build/us/strlib.map).
2. if/else branch layout must match the target's actual physical layout, not just be logically
   equivalent -- verify via diff.py addresses.
3. `(a << 3) + b` compiled as `or` instead of `addu` when b's *value range* (not declared type
   width) is provably confined to the low 3 bits -- type tricks (u8/u16/s32) had zero effect.
4. Two independent adjacent struct-field loads before a branch get freely reordered by GCC's
   scheduler; this reordering was immune to every C-level trick tried (explicit locals in either
   order, `!= 0` vs implicit truthy). Fix: restructure to flat top-of-function local declarations
   matching st0/e_lock_camera.c's established style -- this changed the scheduler's behavior for
   the whole function.
5. The very last diff: an if/else pair (hitboxWidth/hitboxHeight) needed `hitboxWidth` assigned
   FIRST in BOTH branches (matching rcen's literal source order), regardless of which branch has
   the array-lookup value and which has the plain constant. Not derivable from first-principles
   compiler reasoning -- found by diffing against rcen's already-matched e_lock_camera.c.
6. Twice, `touch`ing the edited .c file wasn't enough to force ninja to recompile after a real
   source change (identical SHA-1 across two genuinely different source versions) -- had to
   `rm -f` the specific .o file before rebuilding.

Lesson for future functions in this overlay: when an instruction-order mismatch survives 2+
rounds of targeted C-level fixes, stop guessing from compiler theory and grep src/st/*/ for a
same-named function already matched elsewhere (st0/, rcen/, lib/, etc.) -- copy its exact
declaration/statement shape first.

original INCLUDE_ASM(..., Name) stub's exact target name before deciding whether to wrap.

Function 7: EntitySoulStealOrb + EntityEnemyBlood (e_particles.c), both in one file/build test.
First attempt hand-copied src/st/e_particles.h's bodies, swapping OVL_EXPORT(EInitObtainable)
for extern EInit g_EInitObtainable (confirmed via raw asm the InitializeEntity call target has
no RLIB prefix) -- compiled and linked fine but produced wrong bytes. Root cause (confirmed via
build/us/strlib.map: EntitySoulStealOrb linked 128 bytes past its correct address): the header's
three hardcoded data arrays (angles/sprite offsets/anim frames) were redefined locally instead
of extern'd, even though the exact same bytes already exist as unnamed extracted data in
asm/us/st/rlib/data/6C4.data.s (D_us_80181644/D_us_80181654/D_us_801816B4 -- confirmed
byte-for-byte identical via manual dump). Fix: extern-declare the three D_us_ symbols directly
and reference them by name instead of the header's array names. Byte-exact on the next build.
General lesson: even when a shared header's data VALUES match byte-for-byte, always grep the
overlay's own data/*.data.s for the address(es) referenced in the raw asm before trusting a
shared header's array -- if it's already extracted as unnamed data there, it must be extern'd,
never redefined.
